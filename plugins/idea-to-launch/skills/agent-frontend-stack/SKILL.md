# AI Agent 产品 Web 前端技术栈与交付规范

> 来源：idea-to-launch-kit《AI Agent 产品 Vibe Coding 通用前端技术栈手册》V1.2，已剥离工具包专属流程（阶段编号、`verify.sh`、证据包、是否表）。手册更新时按插件 README 的同步清单核对本技能。

**在 idea-to-launch-kit 工作区里时**（当前目录或上级有 `AGENTS.md` 且有 `docs/手册/`）：以 `AGENTS.md` 和前端手册为准，本技能不另起流程；两者措辞不一致时按工具包执行，并把差异告诉用户。

## 为什么 Agent 产品的前端要单独讲

普通技术栈清单只会说"用 Next.js、React、Tailwind"。Agent 产品的前端还要处理：任务可能跑几秒到几分钟；过程中持续输出文本、步骤和中间结果；Agent 会暂停等用户确认；页面刷新或断网后任务还在后端继续跑；同一任务可能产出图片、视频、音频、文件。**接口成功不等于产品成功，构建成功不等于页面达到交付标准。**

所以这个技能同时规定四件事：默认技术栈、前端架构和数据边界、Agent 交互与任务状态、开发预览和验收。

## 适用边界

默认适用：AI 对话、内容生成、工作流、自动化、多媒体生成产品；内部工具、运营后台、创作工作台、Agent 控制台；桌面浏览器为主、兼顾移动浏览器的 Web MVP；新项目或已有 React / Next.js 项目的迭代。

只能参考、不能照搬：原生 iOS / Android / 鸿蒙、小程序、桌面客户端、浏览器插件；对 SEO 或极致首屏有特殊要求的大型内容站；高实时协同、3D、游戏、超大数据可视化；强监管系统。这些场景仍守状态、安全和验收原则，但要在《前端适配声明》里重新说明技术选择。

## 决策分层

### A 层：所有项目都必须遵守

- TypeScript，开启严格类型检查；
- 接口调用集中管理，不在页面组件里散落 `fetch`；
- **后端是任务状态和业务结果的最终事实来源**；
- 加载、空、成功、失败、等待确认、断线恢复等状态都要设计；
- 密钥、服务商凭证、私密系统提示词不进浏览器；
- 核心页面有合理的桌面端和移动端布局；
- 核心操作能用键盘完成，交互控件有可理解的名称；
- 重要提交防重复，重要删除要确认；
- 通过代码检查、构建检查和**真实浏览器验收**；
- 不能只用 mock 数据宣布"前后端已经完成"。

需求没写也不能忽略的：安全和隐私底线；加载、空、失败和恢复状态；移动端基本可用；核心流程的真实浏览器验收；不把本地界面状态冒充为后端真实任务状态。资料有关键冲突时，编码前用产品语言说明冲突、影响和推荐方案，不在代码里偷偷选。

### B 层：Web MVP 默认方案

| 项 | 默认 |
| --- | --- |
| 运行时 / 包管理 | Node.js 当时的 Active LTS；npm |
| 框架 | Next.js 稳定版，App Router |
| 语言 | TypeScript strict |
| 样式 | Tailwind CSS + CSS 语义变量（Tailwind 4 写在 `@theme`） |
| 图标 | Lucide |
| 测试 | Vitest + React Testing Library |
| 交付门槛 | ESLint、类型检查、生产构建 |

版本取建项目时的稳定版，不写死；在《前端适配声明》里记录实际版本并锁定依赖文件。已有项目优先兼容，不为追新替换稳定框架。

### C 层：出现明确需求后再引入

| 能力 | 建议方案 | 引入条件 |
| --- | --- | --- |
| 无障碍复杂组件 | Radix UI 或 shadcn/ui | 对话框、菜单、下拉框较多 |
| 服务端数据缓存 | TanStack Query | 多页面共享请求，缓存、失效、重试变复杂 |
| 全局客户端状态 | Zustand | 远距离组件共享大量临时状态，URL 和状态提升都不合适 |
| 复杂表单 | React Hook Form + Zod | 动态字段、多步骤、复杂校验 |
| 接口代码生成 | OpenAPI Generator 等 | 后端已有稳定可维护的 OpenAPI |
| 大列表虚拟化 | TanStack Virtual 等 | 实际数据量造成明显卡顿 |
| 富文本 / 代码编辑器、图表、画布 | 按业务选型 | 需求确实需要 |
| 国际化、PWA | 成熟方案 | 已确认多语言 / 离线需求 |
| 前端错误监控、产品分析 | Sentry 等 | 进入真实用户测试或生产；**可能计费，先告知费用并等确认** |
| 端到端测试套件 | Playwright | 核心闭环超过 2 条，或同一闭环反复回归、手工验证成本明显上升 |

没有真实复杂度，就不要用复杂工具制造"看起来专业"的代码。不要一开始同时引入 Context、Redux、Zustand 和 TanStack Query。

## 默认架构

```text
frontend/
├── app/                 # 路由、页面、布局、error.tsx、loading.tsx
│   └── bff/             # 仅需要 BFF 逻辑时创建；不占用被代理转发的 /api/* 路径
├── components/
│   ├── ui/              # Button、Dialog、Input 等通用组件
│   └── layout/          # 顶栏、侧栏、页面容器
├── features/<业务>/      # api/ components/ hooks/ schemas/ types.ts
├── lib/
│   ├── api/             # API 客户端、错误归一化
│   ├── stream/          # SSE / 流式处理
│   └── auth/ media/ utils/
├── config/  styles/  tests/
└── e2e/                 # 引入 Playwright 后才建
```

依赖方向：页面路由 → 业务组件与 Hook → API / Stream / Auth 适配层 → 后端接口。通用 UI 组件不反向依赖具体业务；页面不直接理解后端供应商的特殊字段。已有项目先理解现有结构，做最小范围改动，不一边做业务一边大规模迁移目录和组件库。

渲染：App Router 默认 Server Component；表单、弹窗、实时进度、流式输出、依赖浏览器 API 的部分用 Client Component，**把交互边界缩到必要区域**，不因为一个按钮把整页变成客户端组件。浏览器专属信息（屏幕宽度、Local Storage、浏览器语言）不参与服务端首次渲染，避免 Hydration 问题。

## 状态：先分清四种，再定一个统一任务模型

| 状态类型 | 例子 | 存放位置 |
| --- | --- | --- |
| URL 状态 | 任务 ID、当前页签、筛选 | 路由或查询参数 |
| 服务端状态 | 任务进度、产物、权限、余额 | 后端，前端通过 API 获取 |
| 页面临时状态 | 输入内容、弹窗开关 | 组件 State 或局部 Context |
| 用户偏好 | 主题、侧栏偏好 | Local Storage 或用户配置接口 |

**刷新页面后，前端根据 URL 里的任务 ID 向后端恢复真实状态**，不依赖内存残留，也不用 Local Storage 冒充任务结果。

长任务的统一状态集合（后端名字可以不同，前端在适配层映射成统一含义；未知状态不静默当成成功或失败）：

`idle` · `submitting` · `queued` · `running` · `streaming` · `waiting_user` · `succeeded` · `partially_succeeded` · `failed` · `cancelled` · `disconnected` · `stale`

数据加载另分：`loading`（还没回来）、`empty`（成功但确实没有）、`failed`、`permission_denied`、`not_found`。**接口没返回前不显示"暂无数据"**。

每个状态都要回答用户三个问题：现在发生了什么？我需要做什么？接下来会发生什么？"生成失败"不够；"视频合成失败，已生成的分镜仍然保留，可以重新合成，不会重复扣除前一步结果"才够。

每个状态的展示要求、SSE / 轮询 / 断线恢复、用户确认、防重复提交、取消、语音交互、产物展示见 `references/agent-interaction.md`。

## 与后端的契约（要点）

- 前端只通过后端 API 调业务能力：模型调用、业务规则、权限判断都在后端；前端不直连模型服务，也不在 Next.js 服务端代码里复制后端业务逻辑。
- 页面不拼接口地址；基础 URL、鉴权、超时、错误转换、日志集中在 API 层。
- 后端错误体 `{"error": {"code", "message"}}` → 前端适配层转成 `AppError`（含按 `code` 映射的 `userMessage`），界面只显示 `userMessage`。
- 默认同源：在 `proxy.ts` 里**请求时**把 `/api/*` 转发到运行时读取的 `BACKEND_URL`，原样带回状态码、响应体和每一条 Set-Cookie；不用构建时固定地址的 `rewrites`。
- 不破坏后端已验收的接口契约；需要不兼容修改时先说明影响和迁移办法，确认后再改，并同步更新后端测试。

完整契约、同源代理与真实 IP 透传、环境变量、表单与上传、安全与鉴权、日志见 `references/api-and-security.md`。

## 交付判定

以下任一情况存在，不宣布完成：
- Lint 或类型检查仍有未解释错误；
- 核心接口仍是 mock；
- 核心页面在目标宽度（390 / 768 / 1280 / 1440px）不可用；
- 失败状态会丢失用户输入；
- 重复点击会创建多个任务；
- 刷新后正在运行的任务无法恢复；
- 浏览器 Console 持续报错；
- 实现与确认的设计或需求明显不一致。

每个子阶段结束前：真实启动前后端，用脚本化浏览器在四个宽度截图并收集 Console 错误和失败请求；对接真实后端和真实模型跑通至少一条核心闭环（没有 Key 如实写"待验"）；跑 `lint`、类型检查、`test`（一次跑完退出）、`build`；更新 README。细则见 `references/testing-and-delivery.md`。

## 开工前先判断：后端阶段留下了什么界面

- **纵向切片界面**（会保留到正式产品）：在它上面继续，不另起平行工程；
- **临时验收界面**（不保留）：在第一个前端子阶段废弃，并在文档里记下废弃了什么；
- **没有界面**：从可运行骨架开始。

然后输出《前端适配声明》和当前子阶段开发文档，等用户确认再编码。用户直接要代码时（"帮我把这个页面写出来"），不要停下来等：把适配声明的要点（技术选择、状态映射、偏离项、待确认的接口假设）写进 README 开头，接着写代码。每条接口假设标明代码里先按什么实现、集中在哪个文件，方便对上真实后端时只改一处。缺失的信息先分类：会改变目标用户、核心任务、成本、安全、隐私、交付范围的必须问，一次不超过 5 个、附推荐答案；其余用本技能默认值填上并说明理由。

**没有设计稿时**，先给出简短视觉方向（颜色、字体、密度、圆角、页面结构、关键组件），做一个代表页让用户提意见，改到满意再铺开全站，避免改错返工。
