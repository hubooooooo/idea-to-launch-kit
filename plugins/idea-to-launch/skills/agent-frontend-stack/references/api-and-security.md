## 1. 集中式 API 层

前端只通过后端 API 调业务能力：模型调用、业务规则、权限判断都在后端；不直连模型服务，也不在 Next.js 服务端代码里复制后端业务逻辑。

不破坏后端已验收的接口契约。需要后端做不兼容修改（改字段名、状态值、错误码）时，先说明受影响的调用方、已有数据和迁移办法，用户确认后再改，并同步更新后端的 mock 测试。

```text
UI 组件
  ↓ 调用业务函数
Feature API
  ↓ 调用统一客户端
HTTP / Stream Client
  ↓
Backend API
```

页面不直接拼接口地址；基础 URL、鉴权、超时、错误转换和日志集中处理。这样开发和生产地址不会散落，普通请求和流式请求用同一套配置，错误解释一致，后端字段改名时不用所有组件一起改。

## 2. 最低接口契约与统一错误

每个接口至少明确：方法和路径；请求字段、类型、是否必填；成功返回结构；失败错误码和用户可恢复方式；鉴权与权限要求；是否幂等；超时和重试策略；任务 ID、状态和产物字段；时间、枚举、金额、文件地址的格式。

后端错误体固定为 `{"error": {"code", "message"}}`。前端适配层据此生成 `AppError`，不另造错误协议；`userMessage` 由前端按 `code` 映射成产品语言，未知 `code` 用通用兜底文案：

```ts
type AppError = {
  code: string;
  message: string;
  userMessage: string;
  retryable: boolean;
  requestId?: string;
  fieldErrors?: Record<string, string>;
};
```

界面显示 `userMessage`，调试日志保留 `code` 和 `requestId`。不把原始堆栈、供应商报错或敏感请求内容展示给用户。

## 3. 接口类型来源

- 后端已有稳定 OpenAPI：优先生成类型和客户端；
- 契约还在快速变化：先维护清晰的手写类型和适配层；
- 无论哪种，生成代码之外都保留业务适配层；
- 前后端枚举变化必须有未知值兜底。

TypeScript 只检查开发时类型，证明不了后端实际返回的数据正确。外部数据进入业务层前用 `unknown` 接住、做运行时校验或安全的字段兜底。

## 4. 环境配置与同源代理

- 浏览器可读的配置可以用 `NEXT_PUBLIC_`；**API 密钥、模型密钥、数据库凭证绝不用 `NEXT_PUBLIC_`**。
- 前端环境只存公开配置；开发、测试、生产地址通过配置管理；普通 API 和流式 API 的地址策略一致并经过部署验证。
- **同源默认做法**：在 `proxy.ts`（Next 16 起替代 `middleware.ts`，运行在 Node.js 运行时）里把 `/api/*` 在**请求时**转发到 `process.env.BACKEND_URL`，原样带回状态码、响应体和每一条 Set-Cookie，避免跨域；`app/` 下不再建同名 `/api` 路由。不用 `next.config` 的 `rewrites`：它的目标地址在构建时就固定了，换后端地址要重新构建。
- **真实 IP 透传**：转发时由代理写入访问者真实 IP（如 `x-client-ip`，取自部署平台写入的来源头——腾讯云开发是 `x-envoy-external-address`，其他平台查其文档——并覆盖客户端自带的同名头），同时带上前后端共享密钥（如 `x-proxy-secret` = `PROXY_SHARED_SECRET`）。后端只在共享密钥正确时才信任这个 IP 头。否则后端看到的来源全是前端服务器，登录限流会把所有用户一起锁住。
- 前端本地配置写在 `frontend/.env.local` 并被 `.gitignore` 排除，仓库只提交 `frontend/.env.example`。
- `BACKEND_URL` 和 `PROXY_SHARED_SECRET` 都在运行时读取，没配时代理返回 503 统一错误；`npm run build` 不依赖它们。本地 `.env.local` 写 `BACKEND_URL=http://localhost:8000`，线上写进平台环境变量。

## 5. 表单、模型配置和上传

表单：
- 必填项、格式、长度和限制在提交前可见；校验错误靠近对应字段；
- 提交失败后保留用户输入；多步骤表单保存草稿或说明离开会丢失；
- 文本框支持合理的粘贴和换行；错误不只用红色，还要有文字。

模型和供应商配置：
- 默认模型必须真实存在于可选列表；
- 已保存但暂时不可用的模型显示"不可用"，不偷偷切到第一项；
- 模型名称、能力、成本提示和限制来自统一配置；
- 配置变化后，当前任务用了哪个版本可追溯；
- 用户看不到的内部模型路由，不伪装成用户的明确选择。

上传：
- 上传前说明格式、数量和大小限制；
- 前端校验扩展名之外，真实类型由后端验证；
- 显示进度、失败原因和重新上传；允许删除或替换未提交的文件；
- 大文件用后端支持的分片或直传；
- 私有文件不依赖永久公开 URL。

## 6. 安全与隐私底线

禁止放进前端：模型服务 API Key；数据库密钥；第三方服务私钥；私密系统提示词；后端管理员凭证；只应服务端知道的业务规则。

鉴权：
- 默认：登录（邀请码或账号）成功后由后端签发会话，放在 Secure、HttpOnly、SameSite 合理配置的 Cookie 里；前端不自行保存 token；
- 不把长期访问令牌放进 Local Storage 或 Session Storage；
- 同时考虑 CSRF、XSS、会话过期和跨设备退出；
- 权限判断由后端执行，前端隐藏按钮不等于权限控制。

内容安全：
- 用户或模型生成的 HTML 默认不可信；Markdown 渲染限制危险标签和链接；
- 外部链接明确打开行为，必要时加安全属性；
- 文件名、富文本和 URL 不直接拼进 DOM；
- 日志、埋点和报错里不记完整提示词、隐私文件和密钥。

高成本操作（真实扣费、发布、群发、删除、覆盖、外部系统写入）：前端明确展示影响；用户最终确认；后端再次校验权限和幂等；页面保留结果或审计入口。

## 7. 日志、监控和产品分析

- 前端错误至少记：时间、页面、错误码、请求 ID 或任务 ID、应用版本、是否可恢复；不上传用户完整输入、生成内容、私密文件或凭证。
- 产品埋点只在需求或指标方案明确后实施，事件名表达业务行为（如 `generation_submitted`、`artifact_downloaded`）；埋点不阻塞核心操作，埋点失败不导致任务失败。
- 接入 Sentry 等可能计费的第三方服务前，先告知费用量级并等用户确认。
