# 工程底线与默认实现规则

`[A]` 强制底线、`[B]` 默认方案、`[C]` 按需模块。没单独标记的解释段落跟随它前面那条规则。

## 1. 后端与 API

- `[B]` 可复用的业务能力默认在后端实现，并能通过 API 或等价的自动化入口独立验证。终端专属能力（端侧模型、摄像头实时处理）可以留在客户端，但业务规则不复制多份。
- `[B]` 新建公开 API 默认以 `/api/v1` 开头。内部 MVP 可以先用 `/api`，但要集中定义；已有项目保留现有前缀。对外发布或出现不兼容变化时建立版本策略，不为形式统一批量改坏已有客户端。
- `[A]` 每个 API 定义请求结构、响应结构和错误情况；内部调试接口也不返回无约束数据。
- `[A]` 前端只通过受控 API 使用后端能力，不直接读数据库或秘密存储。
- `[A]` 长时间任务保存可恢复的任务状态，不只依赖内存变量，也不让一次 HTTP 请求无限等待。耗时较长的 AI 能力提供 SSE 或"提交任务 + 轮询状态 + 获取结果"的异步接口，二选一在阶段文档里写明；这个能力要能脱离正式前端独立验证。
- `[A]` 错误响应格式统一为 `{"error": {"code": "...", "message": "..."}}`，不把堆栈展示给用户。

### 使用 SSE 时的默认事件约定

- 事件序列：`chunk` 零到多次 → 以 `done`（含完整结果）或 `error` 结束，二者必居其一。
- **流中途失败必须发 `error` 事件**，携带与普通响应相同的统一错误结构；不允许静默断流，不把异常堆栈写进流。
- 易踩的坑：模型 SDK 在**构造客户端阶段**就可能抛错（比如没有 Key），这类错误发生在重试逻辑之外。在调用链最外层做统一兜底，保证任何阶段的失败都走 `error` 事件。
- 前端会把"连接关闭但没收到 `done`"当作断线去回查任务状态，所以后端漏发 `done` 会让成功的任务看起来像失败。

## 2. 数据与状态

- `[A]` 重要业务数据和长任务状态必须持久化，进程重启后可恢复。载体可以是数据库、带 schema 版本的结构化文件、对象存储或现有平台服务，按数据关系、并发和查询需求决定。
- `[C]` 多实体关系、事务、复杂查询或并发修改触发关系型数据库；选了就默认用 SQLAlchemy 定义模型、Alembic 管理变更。
- `[A]` 用结构化文件持久化时，定义 schema 版本、原子写入（写临时文件再改名）、损坏处理、并发边界和未来迁移路径。
- `[B]` 图片、音频、视频和大文档存文件或对象存储，元数据和关联关系存在选定的结构化存储里。
- `[A]` 状态用明确的枚举或受控值，遵守阶段文档里的流转规则。先定义当前阶段能确认的状态；新增状态要考虑旧数据兼容，不为"永不改枚举"提前猜完所有未来需求。
- `[A]` 删除重要数据前确认；生产环境优先软删除或审计记录。
- `[A]` 会有多个使用者的业务记录，从第一张表起带归属字段（如 `owner_id`）。当前阶段还不做登录时，先写入固定的默认归属，避免上线前做数据迁移。查询和修改一律在后端按当前使用者过滤，前端隐藏不算权限控制。
- `[B]` 数据读写集中在 repository 层，不散落在路由和服务里。这样本地 SQLite 和线上托管数据库可以是同一接口的两种实现，跑同一套测试。

## 3. AI 与 Agent

- `[B]` 模型、Agent、RAG 调用集中在清晰的服务或领域层，不散落在路由和页面组件里；目录名可以延续现有项目。
- `[A]` Prompt 独立管理、可版本追踪，不把大段 Prompt 混在接口代码里。
- `[A]` 模型名、base_url、超时和参数通过配置读取，不硬编码。
- `[A]` 模型调用处理超时、失败和有限次重试，包括 SDK 初始化失败（见第 1 节 SSE 部分）。
- `[A]` 模型输出必须结构校验，不能假设模型总会返回正确格式。结构化产出优先用"模型输出标准格式 + 后端确定性解析 + Pydantic 强校验"；校验失败走有限重试，仍失败走统一错误。

### 格式约束三件套

模型"不按格式输出"是常态（要求 `#` 标题却给 `1.1` 编号，要求 3–5 条却给十几条），只靠重试往往烧钱又解决不了。同时做到：

1. **Prompt 写正反例**：给正面示例，并明确禁止的反例（"用 `#` 开头，禁止 `1.1` 编号"），不只写抽象描述。
2. **解析器要宽容**：确定性解析同时兼容几种常见等价格式（`#` 标题、中文序号、点分编号），而不是只认一种、靠重试硬扛。
3. **数量 / 内容约束不遵守 ≠ 解析错误**：像"每章 3–5 个子标题"这类约束，模型常超量但内容正确。记为质量瑕疵交给用户判断，不反复重试烧钱。

### 其余规则

- `[B]` 记录模型、耗时、Token 用量和错误类型；不记的内容见第 4 节。
- `[A]` **高风险、不可逆、涉及外部发送或费用的动作，由确定性代码和权限策略约束。**
- `[B]` 固定业务流程默认由代码状态机编排。
- `[C]` 只有产品确实需要动态选工具或规划步骤时，才让模型在明确的工具白名单、参数校验、预算、最大步数、超时和人工确认点内决策。不允许无限自主执行。
- `[A]` 关键人工确认点持久化，刷新页面、服务重启或换终端后仍能继续。

## 4. 配置与安全

- `[A]` API Key、数据库密码等敏感信息只放后端可访问、不提交到仓库的秘密载体。本地默认 `.env`，也可以用系统钥匙串、部署平台 Secret 或产品的后端安全设置；普通配置可以用 YAML、JSON 或数据库。
- `[A]` 用 `.env` 时加入 `.gitignore`，只提交不含真实值的 `.env.example`。用其他载体时也提供不含秘密的配置说明。
- `[A]` 模型 API Key 只能由后端读取，不进前端代码或构建产物。
- `[A]` 产品允许用户在前端录入 Key 时，前端只能把它提交给受保护的后端接口；响应脱敏、日志不记录，传输和存储满足产品安全等级。
- `[A]` 上传文件检查格式、真实内容类型（不只看扩展名）、大小和安全文件名，防止路径遍历；高风险场景还要病毒扫描和内容隔离。
- `[A]` 日志不记录密码、API Key 或完整用户文档。
- 密钥变量名建议包含 KEY / SECRET / TOKEN / PASS / ACCESS 之一，方便扫描工具识别；测试代码里的假 Key 用明显的短值（如 `fake-for-test`），避免被扫描误判为真密钥。

## 5. 文件处理边界

- `[B]` Word 默认只支持 `.docx`，不支持旧版 `.doc`。
- `[B]` PDF 默认只支持能选择、复制文字的文件。
- `[C]` 纯图片扫描版 PDF 只有需求明确要求时才引入 OCR。
- `[A]` 本地文件通过结构化存储记录文件名、受控路径、状态、上传时间和业务归属，不靠散落的目录猜测资产关系。

## 6. 环境与依赖版本

后端：

| 项目 | 默认 | 层级 |
| --- | --- | --- |
| Python | 3.12.x，虚拟环境放 `backend/.venv/` | B |
| FastAPI / Pydantic / pytest | 建项目时的稳定版 | B |
| SQLAlchemy | — | C |
| Alembic | 用关系型数据库时默认配套 | C |

Web 前端（选了 Web 端才用，细节见 agent-frontend-stack）：Node.js 当时的 Active LTS、npm、Next.js + TypeScript + App Router、Tailwind CSS、ESLint + TypeScript 检查。

版本管理：
- 新项目在 `requirements.txt` 或 `pyproject.toml + 锁文件` 中二选一，记录可复现版本；已有项目延续原有方式。
- 前端依赖写入 `package.json` 并提交与包管理器匹配的锁文件；同一子项目不无理由混用 npm、pnpm、yarn。
- 没有迁移理由和回归验证，不升级核心依赖大版本。
- 加辅助库时说明用途，把版本约束和验证结果写进依赖与交接文档。
- 这里的版本是经过验证的默认基线，不是永久锁死；版本失去维护、安全支持或与运行环境不兼容时，提出单一升级方案并验证迁移。
