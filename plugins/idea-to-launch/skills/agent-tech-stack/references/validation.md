# 双层验收、效果评分与重启恢复检查

## 目录

1. 第一层：mock 自动化测试
2. 第二层：真实模型端到端冒烟（含冒烟记录格式）
3. 效果标准缺失时的默认评分法
4. 重启恢复检查
5. 每阶段验收流程

涉及模型调用的核心链路，两层都要做。不涉及模型的纯工程阶段可以不重复调用真实模型，但仍要跑相关自动化和集成测试，并在阶段文档里说明。

---

## 1. 第一层：mock 自动化测试（每次开发完成必跑）

- pytest 写后端测试；模型调用一律 mock，离线可跑。前端和其他终端用各自技术栈的测试工具。
- 覆盖：业务逻辑、状态流转、参数校验、错误路径、模型输出解析器（纯函数单测是重点）。
- 至少 5 条有意义的用例。一条空测试"通过"什么也证明不了。
- 跑测试时清空真实 Key 的环境变量，确保测试真的没碰网络。

## 2. 第二层：真实模型端到端冒烟（阶段验收前必做）

mock 测试**永远覆盖不到**：
- 认证与 SDK 初始化（无 Key、错误 Key、过期 Key 的表现）；
- 真实网络下的超时、限流、重试；
- 模型真实输出质量：结构合规率、内容质量、Prompt 约束是否生效。格式合规率区分"首测即合规"和"重试后才合规"；数量 / 内容约束的遵守率单独记，交用户判断容忍度，不当解析失败反复重试；
- 真实延迟：首字时间、整体耗时是否满足需求。

**最低要求**：每种不同的模型调用契约、每条关键用户链路，至少跑通一条"真实输入 → 真实模型 → 持久化 / 返回 → 用户可查看结果"的完整路径，如实记录模型、时间、成本和结果。多个接口复用同一个已验证的模型服务时，不必为凑数重复付费调用，在阶段文档里写明覆盖关系即可。

**流式接口**：用 `curl -N` 调 SSE 接口并计时，确认首个 chunk 的时间达标、事件序列以 `done` 或 `error` 正确收尾、失败时错误结构统一。

### 冒烟记录：机器写，不手填

"跑过了"不能只在对话里说。在第一个要调真实模型的阶段写一个冒烟脚本（默认 `scripts/smoke.py`，从 `backend/.env` 读 Key），它跑每条真实链路，把结果追加到一个记录文件（默认 `docs/` 下按阶段存放的 `冒烟记录.md`）：

```markdown
# 冒烟记录（冒烟脚本自动写入，不得手填）
- 产品：{产品名}
- 阶段：{阶段名}
- 模型：{厂商 / 模型名}
- 写入时间：{YYYY-MM-DD HH:MM:SS}

| 时间 | 链路 | 请求 ID | 输入 token | 输出 token | 首字耗时 | 总耗时 | 结构校验 | 重试次数 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-11-02 16:30:12 | 生成大纲 | req_xxx | 812 | 455 | 0.9s | 6.2s | 首测合规 | 0 | 通过 |
```

规则：
- 每次真实调用一行；时间列用 `YYYY-MM-DD HH:MM:SS`；请求 ID 取厂商返回的，没有写 `-`；结果列只写 通过 / 失败 / 瑕疵待打分。
- 不写 Key，不写完整的用户输入和模型输出（样例另存，交用户打分）。
- **冒烟之后又改了代码，记录就过期了**：`backend/`、`frontend/`、`scripts/` 下有比记录更新的代码文件时，要重跑。
- 没有 Key 时不跑脚本、不造记录，如实写"待验"。

## 3. 效果标准缺失时的默认评分法

需求里没有可执行的效果标准时，不要自己发明数字然后宣布通过。第一次真实冒烟时这样定：

1. 用真实输入跑出 5–10 条样例，整理成用户能直接看的形式（文档、对话记录、图片等）。
2. 按产品类型给评分表，维度不超过 5 个，每个 1–3 分：

   | 产品类型 | 默认维度 |
   | --- | --- |
   | 写作 / 生成类 | 覆盖要求、结构合规、语言质量、事实无误、长度合适 |
   | 问答 / 知识库类 | 回答正确、引用来源、不编造、简洁、拒答边界 |
   | 分析 / 数据类 | 结论正确、数据引用准确、推理可追溯、格式合规 |
   | 多媒体类 | 符合描述、质量可用、风格一致、无违规内容 |

3. 用户逐条打分，标出"不能接受"的样例。
4. 据此写出本项目的验收标准（如"5 个维度平均不低于 2 分，且无不能接受项"），记进项目的决策记录，后续阶段沿用。
5. 格式合规率、内容质量分、数量约束遵守率分开统计。数量超标记为瑕疵交用户判断，不触发重试。

## 4. 重启恢复检查

"数据重启后还在"要实际验证，而且最好不让写代码的一方自己给自己打分：**起服务、写标记、杀进程、再起、读回比对**这几步由一个独立的检查脚本来做，产品只提供四个和自身相关的动作。默认放在 `scripts/restart-check.sh`：

| 调用 | 做什么 | 标准输出最后一行 |
| --- | --- | --- |
| `restart-check.sh start` | 用临时数据位置起一个服务实例，等端口能响应再返回 | 服务进程 PID（只有数字） |
| `restart-check.sh write <标记>` | 通过产品自己的写入路径（接口或服务层）写一条带该标记的记录 | 记录 ID |
| `restart-check.sh read <ID>` | 通过产品自己的读取路径按 ID 读回 | 记录里的标记原文 |
| `restart-check.sh stop` | 清理：停掉还在跑的实例、删临时数据 | 任意 |

检查流程：生成随机标记 → `start` 得 PID1，确认进程在跑 → `write` 得 ID → 由检查方自己 `kill -9` PID1 并确认进程已不在 → 再 `start` 得 PID2，要求 PID2 ≠ PID1 → `read ID` 的输出必须与标记完全一致 → 杀掉 PID2，调 `stop`。任一步不符即不通过，并写明卡在哪一步。

写钩子时注意：
1. **临时数据位置**：由环境变量（如 `RESTART_CHECK_DIR`，一个空临时目录）指定，两次 `start` 都把数据库、上传目录放在它下面，第二次才能读到第一次写的数据；不碰真实数据。
2. **不调真实模型**：清空模型 Key；`write` 优先走不需要模型的接口。唯一的写入接口要调模型时，用环境变量让服务启动时换上 mock 测试用的同一个模型替身，其余代码与正式服务一致。
3. **`start` 的写法**：`nohup … > "$RESTART_CHECK_DIR/server.log" 2>&1 &` 放后台并重定向输出（否则调用方会一直等）；不用 `--reload`（否则 PID 是看门进程，杀掉后子进程还占着端口）；等端口能响应后只打印 PID。
4. **端口被占**：不杀别人的进程，直接非 0 退出并打印原因。
5. **输出干净**：四个动作的标准输出最后一行就是结果，日志走标准错误或文件。

## 5. 每阶段验收流程

完成当前阶段后：

1. 启动本阶段涉及的服务。
2. 跑第一层 mock 测试。
3. 用真实 Key 跑冒烟脚本完成第二层冒烟（没 Key 时明确声明待验，不造记录，不拿 mock 冒充）。
4. 用接口文档或自动化测试验证核心后端流程。
5. 涉及界面时跑类型检查、代码检查和关键交互验证；界面会保留到正式产品时，检查桌面和移动端宽度（临时验收界面不需要）。
6. 按当前阶段技术开发文档逐条验证验收标准。
7. 如实说明哪些通过、哪些没通过及原因。
8. 更新 README：启动命令、环境变量、验证步骤。
9. 停掉不再需要的临时服务、释放端口；用户要求保留预览时，报告还在运行的地址和进程用途。
10. 关键业务规则（评分公式、判定阈值、话术标准等）还没冻结时，用"临时方案 + 显式标注 + 可配置"跑通全链路，在交付清单里列出仍待冻结的规则；不当作已完成，也不因此卡住开发。
11. 交付时给用户一份自检结果：测试通过数 / 总数、真实冒烟是否跑过（引用冒烟记录）、密钥是否排除在代码和产物之外、重启恢复是否通过、前端构建是否通过。这几项以命令和脚本的实际输出为准，不凭记忆填写；任一项不通过就不宣布阶段完成。

不能通过删测试、隐藏报错、用 mock 冒充真实验证或降低验收标准来声称"开发完成"。Agent 是否通过验收，以产品需求和当前阶段技术开发文档为准；本技能只规定"必须验证"和验证方法，不替具体产品定指标。
