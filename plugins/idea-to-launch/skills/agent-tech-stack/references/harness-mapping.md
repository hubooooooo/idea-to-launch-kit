# Harness 组件 → 产品实现对照表

用户带着 Agent 工坊（agent-prd 技能或工坊引擎）产出的 `方案.md` 来时使用。方案里的组件选型沿用课程《Learn Claude Code》的 17 章叫法（s01–s17）。写《技术适配声明》第 3 节"触发的按需模块"时，逐项对照方案的组件选型表：选中的组件写"采纳"或"不采纳及原因"，方案放弃的组件默认不做，不抛开方案另起一套。

下表的"MVP 默认实现"是最小做法，不是上限。

| 方案里的组件 | 对应的工程规则 | MVP 默认实现 | 什么时候不做 |
| --- | --- | --- | --- |
| s01 Agent Loop | AI 与 Agent：循环由代码控制 | 后端一个 Agent 服务模块；最大步数、超时、预算上限写成配置，超限即停并记录 | 只调一次模型的产品：直接一个 API 调用 |
| s02 工具系统 | 工具函数加 Pydantic 参数校验 | 每个工具一个函数，输入输出有模型类；工具不直接暴露为公网接口 | 没有工具调用 |
| s03 权限系统 | 底线：高风险动作由确定性代码和权限策略约束 | 工具分三档：放行、需确认、禁止，写在代码里的策略表；需确认的动作返回"待确认"状态，由界面让用户点确认 | 只读、不写不删不花钱：保留禁止清单即可 |
| s04 钩子系统 | 结构化日志与审计 | 每次工具调用、权限判定、模型调用记一行到审计表（SQLite 表或 JSONL），带时间、用户、结果 | 不会不做：审计是底线，至少记日志 |
| s05 任务规划 | 一般不单独实现 | 多步固定流程交给代码状态机（见 s16）；真需要模型列计划时，计划存成任务记录 | 单步交付的产品 |
| s06 子 Agent | 一般不做 | MVP 不拆子 Agent；需要并行分析时先用后台任务 | 几乎所有 MVP |
| s07 技能加载 | 提示词片段与知识目录 | 领域规则、话术写成文件，按场景拼进系统提示词；需要检索时才上 Chroma | 知识一页纸写得完 |
| s08 上下文压缩 | 会话上下文裁剪 | 只带最近 N 轮加一段摘要；长文档先截取再给模型 | 单轮短交互 |
| s09 记忆系统 | 按需模块：多实体关系的 SQLite 表 | 用户或实体档案表，每条记忆带来源和时间戳；写入和删除走 s03 的确认 | 不需要跨会话记住任何事 |
| s10 任务系统 | 按需模块：长耗时任务的持久化记录 | 任务表：状态、进度、结果，重启后还在 | 没有跨请求的长任务 |
| s11 后台任务 | "提交 + 查询状态"或 SSE | 慢操作提交后返回任务号，前端轮询或 SSE 看进度；任务队列按按需模块的阈值再上 | 每次请求几秒内完成 |
| s12 定时调度 | 部署平台的定时触发 | MVP 先做成可手动调用的接口；上线后由平台定时任务调用 | 由用户动作触发的产品 |
| s13 Agent 团队 | 不做 | MVP 不做多 Agent 协作 | 全部 |
| s14 MCP 插件 | 不做 | 外部系统直接写成工具函数调它的接口，不接 MCP | 全部 |
| s15 集成 Harness | 不是单独模块，是 Agent 服务模块的组织方式 | 把选中的组件装进同一个循环，一个入口函数 | 方案没选多组件时 |
| s16 工作流运行时 | 固定流程由代码状态机编排 | 流程写成状态机或顺序函数，只在真需要动态选工具的那一步让模型决策 | 全程都要模型临场决定（少见） |
| s17 目标闭环 | 验收机制：测试与交付自检 | "做完没有"由测试和验收记录判定；运行时的自动完成判定只在需求明确要求时实现 | 几乎所有 MVP 的运行时 |

方案里的其他内容：
- 工具清单的"权限"列（allow / ask / deny）就是 s03 的三档。
- "安全边界与降级策略"写进阶段文档的错误处理。
- "技术栈与部署形态"里的环境变量名可以沿用，放进 `.env.example`，按配置与安全规则处理；方案里的技术栈只作参考，默认基线仍以本技能为准，差异写进技术适配声明第 4 节。
- "可观测性"里的日志、指标、轨迹由 s04 的审计表承担，不另起监控系统。
- 工坊的 `skeleton/` 不是本项目的代码，不读、不复制。
