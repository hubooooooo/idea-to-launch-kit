# 文档模板：需求补全清单、技术适配声明、阶段技术开发文档

## 目录

1. 需求要覆盖的八类信息
2. 《需求补全清单》
3. 《技术适配声明》
4. 《阶段技术开发文档》

文件默认放在项目的 `docs/` 下；项目已有文档约定时按项目约定。

---

## 1. 需求要覆盖的八类信息

不要求用户设计数据库或 API；缺失的技术表达由你在技术适配声明和阶段文档里补全。需求应覆盖：

1. **目标用户与核心任务**：谁在什么场景下用它完成什么任务？
2. **输入、过程和产物**：用户提供什么，过程中要看见或确认什么，最终得到什么？哪些内容要长期保留？
3. **Agent 主链路**：一次生成、分阶段确认、多轮对话，还是动态调用工具？哪些关键步骤必须由用户确认？
4. **效果验收标准**：什么叫"生成得好"？允许什么瑕疵、由谁判断？
5. **交付阶段和优先级**：最小可用版本必须包含什么？哪些可以后做？
6. **模型与成本约束**：有没有指定或禁用的模型厂商？单次任务或每月成本上限？
7. **数据与非功能要求**：是否涉及个人信息、企业机密或受监管数据？用户量、响应时间、文件限制、部署位置有没有硬要求？
8. **上线与账号**：内部试用还是对外？登录方式有无要求？云费用预算？（登录方式可以先默认"邀请码换 HttpOnly Cookie 会话"让用户确认一次；不论哪种，业务表从第一张起带归属字段。）

冲突处理：业务行为以需求为准；安全、隐私、数据保护和验收真实性的底线不被普通需求默默覆盖；默认技术方案可以因需求、现有系统、部署环境或成本调整，但要写进技术适配声明，说明理由、影响和恢复条件。无法裁决的业务冲突，或会显著改变成本、数据安全、交付终端的冲突，明确指出，不自行猜测。

## 2. 《需求补全清单》

需求不完整是常态。不要直接用默认值填满然后往下跑，也不要一次抛出一堆问题。

```markdown
# 需求补全清单

## 必须问（本轮不超过 5 个）
### 问题 1：{一句话}
- 为什么重要：
- 选项：A / B / C
- 推荐：{哪个，一句理由}
- 不选的后果：
（可以只回复"按推荐"）

## 可默认（已用默认值填上，请确认）
| 缺口 | 默认值 | 理由 |
| --- | --- | --- |

## 已发现的矛盾（如有）
- 矛盾点 / 推荐裁决
```

**必须问**：会改变目标用户、核心任务、成本、安全、隐私或交付范围的（验收标准完全缺失；没说是否涉及个人信息；没说成本上限；主链路是一次生成还是分步确认没说清；内部试用还是对外）。**可默认**：其余（文件格式限制、响应时间、是否保留历史、API 前缀）。

用户回答后更新清单；还有必须问的就再来一轮，仍不超过 5 个。清单全部关闭后再写技术适配声明。决定记进项目的决策记录，后面不再重复问。

## 3. 《技术适配声明》

每个项目第一次动手前，以及需求、交付终端或既有架构显著变化时，先检查环境和代码，再输出这份声明。全部采用默认项时，用户不必逐项审批技术名词，但仍要确认下面三件事再开工；偏离会显著改变成本、安全、数据迁移、交付终端或已有功能时，列入第 6 节等用户决定。

```markdown
# 技术适配声明

## 1. 产品形态判断
- 产品类型与核心任务：
- 核心交互：一次生成 / 多轮对话 / 分阶段确认 / 动态工具调用 / 其他
- 开发路径：后端先行 / 纵向切片
- 验收界面：无 / 临时验收界面（正式前端开始时废弃）/ 纵向切片界面（保留到正式产品，需用户确认）
- 当前阶段范围：

## 2. 采用的默认方案
- 方案：采用原因（每项一句话）

## 3. 触发的按需模块
- 模块：由哪条需求触发；当前阶段是否引入

## 4. 偏离或暂缓的默认方案
- 默认方案：替代方案；原因；影响；什么条件下重新评估

## 5. 强制底线检查
- 密钥与隐私：通过 / 待处理
- 数据与任务可恢复：通过 / 待处理
- 输入输出校验：通过 / 待处理
- 错误与日志边界：通过 / 待处理
- 测试与真实模型验收：计划是什么

## 6. 需要用户决定的问题
- 用决策卡格式（问题 / 选项 / 推荐 / 不选的后果），不超过 5 个；已定的不再问；没有写"无"

## 7. 子阶段规划
- 依据：需求的"交付阶段与优先级" + 第 1 节的开发路径
- 后端阶段：一行一个子阶段，写"编号 / 打通的主链路片段 / 用户验收时做什么"；简单产品可以只有一个
- 前端阶段：默认按 agent-frontend-stack 的前端子阶段 0–4，用不到的写"合并到 X"
- 调整规则：验收后要合并、拆分或增减子阶段，先改这一节并记录原因，再写下一份阶段文档
```

用户审阅时只需确认三件事：
1. 对目标用户、核心任务的理解对不对，子阶段规划（几轮、每轮做什么、每轮验收什么）是否符合交付优先级；
2. 有没有新增需求没要求的费用、外部平台、数据上传或上线范围；
3. 被暂缓的能力会不会影响当前阶段验收。

示例结论："分阶段确认的多媒体创作 Agent"——采用 Python、FastAPI 和 Web 默认栈；人工确认、图片预览和任务恢复是核心体验，选纵向切片；MVP 单用户、资产以图片视频为主，暂缓关系型数据库，先用带 schema 版本的结构化文件（原子写入），出现多用户、复杂筛选或并发修改时再迁移。这不是让用户挑数据库，而是让取舍可见、可追溯。

开始开发前，这四个问题的答案都应在阶段文档里：当前阶段做出什么结果？怎么启动和操作？怎么判断验收通过？出错时该把什么报错和现象交出来排查？

## 4. 《阶段技术开发文档》

每个阶段一份，从需求和技术适配声明推导。模板按需裁剪，但不删与本阶段有关的风险、测试和验收内容。

```markdown
# 第 N 阶段技术开发文档｜{阶段名称}

> 本文档只覆盖第 N 阶段，开发时不提前实现其他阶段的能力。

## 一、阶段目标
- 交付范围（对齐子阶段规划中本阶段那一行）
- 阶段产物
- 验收标准（对齐需求，可细化）
- 明确不做（列出后续阶段的能力，防止范围蔓延）
- 本阶段打通的主链路片段

## 二、技术适配摘要
- 引用《技术适配声明》的结论
- 本阶段采用的默认方案 / 启用的按需模块及触发需求 / 偏离或暂缓及理由
- 开发路径：后端先行 / 纵向切片

## 三、技术栈与模型
- 本阶段实际用到的组件（不需要的明确说不引入）
- 模型：厂商、模型名、配置项

## 四、环境与配置
- 不含秘密的配置项和 `.env.example`
- 需要用户提供什么（如 API Key，验收前提供即可）
- 端口、外部工具和依赖服务

## 五、项目结构
- 本阶段新增的目录与文件职责

## 六、数据、资产与状态
- 持久化方式及原因
- 数据表或结构化文件：字段、类型、schema 版本、说明
- 图片 / 音频 / 视频 / 文档资产：位置、元数据、关联和清理规则
- 状态机：状态、转换、恢复方式和兼容策略

## 七、API / 工具设计
- 每个接口：方法、路径、请求体、响应体、错误码、校验规则
- 长耗时接口用 SSE 还是"提交 + 轮询"
- 用 SSE 时写明事件序列与 done / error 的数据结构
- 动态 Agent 写明工具白名单、权限、预算、最大步数和人工确认点

## 八、Prompt 设计
- 每份 Prompt 的角色、输入变量、输出格式、约束
- 模型输出与结构化存储的关系（谁解析、校验规则）

## 九、验收界面或纵向切片（按需）
- 是否需要最小界面；临时验收界面还是纵向切片界面
- 功能上限、目标终端和关键交互

## 十、测试要求
- 第一层 mock 测试：逐条列出用例
- 第二层真实冒烟：用哪条真实输入跑通哪条链路、记录什么指标
- 数据恢复检查（`scripts/restart-check.sh` 是否要新建或改写）、错误路径、文件安全和关键交互测试

## 十一、验收清单
- 非技术人员照着点就能验证的逐条操作项（checkbox），覆盖需求的验收标准

## 十二、风险与待确认项
- 已知限制、成本、安全与迁移风险
- 改动影响：对最终用户、对后续维护分别有什么影响；有变差的地方写明原因
- 必须由用户决定的问题；没有写"无"

## 十三、交接给下一阶段
- 哪些数据 / 能力 / 代码已就绪，下一阶段直接复用什么
```

写作要求：
- 从需求和技术适配声明推导，不发明需求里没有的业务规则；需求内部有张力的地方给一个推荐裁决，只有重大影响项才等用户确认。
- 验收清单是"照着点就能验证"的操作项，不是技术指标罗列。
- 结构校验管不到的细微瑕疵（如个别格式笔误），在验收清单里注明由用户判断容忍度。
- 一个阶段验收通过后，按子阶段规划的下一行用同一模板写下一份；产品形态或架构约束发生重大变化时，先更新技术适配声明。
