# AI Agent 产品后端技术基线与工程规范

> 来源：idea-to-launch-kit《AI Agent 产品 Vibe Coding 通用技术栈手册》V2.4，已剥离工具包专属流程（阶段编号、`verify.sh`、证据包、是否表）。手册更新时按插件 README 的同步清单核对本技能。

**在 idea-to-launch-kit 工作区里时**（当前目录或上级有 `AGENTS.md` 且有 `docs/手册/`）：以 `AGENTS.md` 和手册为准，本技能不另起流程；两者措辞不一致时按工具包执行，并把差异告诉用户。

## 这个技能要解决什么

用一套稳定的默认技术基线减少无意义的选型，同时允许产品形态真正需要的例外；**先验证核心链路和 Agent 效果，再逐步完成正式产品**。

它不替代具体产品的需求文档，也不要求所有 Agent 产品长成同一种架构。工程底线保持不变，默认方案根据需求、现有代码和运行环境做一次适配，例外写清楚。

## 三层规则：先分层，再动手

每条技术要求都归入下面一层。不要把默认方案伪装成不可违反的原则，也不要用"需要灵活"绕过底线。

| 层级 | 含义 | 处理方式 | 典型内容 |
| --- | --- | --- | --- |
| A 强制底线 | 与安全、数据、可恢复性、可验证性直接相关 | 必须遵守；法律或公司规范不同时，取更严格的 | 密钥不进前端和仓库、输入输出校验、长任务可恢复、错误不泄露堆栈、真实测试不冒充 |
| B 默认方案 | 适合大多数从零开始的 Agent MVP | 默认直接采用；触发适配条件时给出**一个**替代方案并说明理由 | Python、FastAPI、Pydantic、pytest、Web 端 Next.js、`/api/v1` |
| C 按需模块 | 只有特定需求出现时才有价值 | 需求或现有代码触发后才引入，不为"技术栈完整"预装 | SQLAlchemy、Alembic、Chroma、OCR、任务队列、对象存储、SSE |

判断顺序固定：**先检查强制底线 → 再判断默认方案是否适配 → 最后只引入被需求触发的按需模块。**

适配不是罗列十种框架让用户挑，而是给出一个推荐结论，用产品语言解释少量关键取舍。

## 默认后端技术基线（B 层）

从零开始、没有既有系统约束时直接采用，不做开放式选型：

| 层 | 默认方案 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.12.x | 与常见云托管镜像 `python:3.12-slim` 一致；现有项目沿用已有版本，但上线前要在目标版本下跑通测试 |
| 框架 | FastAPI | 把能力做成可测试、可调用的 API |
| 数据校验 | Pydantic | 校验接口和模型结构化输出 |
| 测试 | pytest | 业务逻辑与错误路径 |
| 代码管理 | Git | 新项目初始化并配置 `.gitignore`；已有仓库不重复初始化 |
| 模型调用 | 官方 SDK 或经过验证的兼容接口 | 厂商和模型名由需求或第一阶段文档确定，本技能不固定 |

按需模块（C 层）——**只有触发条件出现才引入**：

| 触发条件 | 默认模块 | 不该引入的情况 |
| --- | --- | --- |
| 多实体关系、筛选统计、事务、用户账户、并发修改 | SQLite + SQLAlchemy + Alembic；生产优先评估 PostgreSQL | 单用户、本地、以资产文件为主且只需简单索引：先用带 schema 版本的结构化文件 |
| 文档语义检索、知识库问答 | Chroma 持久化模式 | 没有 RAG，或小规模全文可以直接搜 |
| 读取或生成 Word | python-docx | 没有 `.docx` 需求 |
| 可复制文字的 PDF | pypdf | 没有 PDF 需求 |
| 扫描件、图片文字识别 | OCR（方案在阶段文档里选定） | 只处理文本 PDF |
| 长耗时任务和并发执行 | 持久化任务记录；满足任一条再上任务队列：多实例共同处理、同时运行的长任务常超过 5 个、单任务超过 10 分钟且必须跨重启续跑 | 短请求、单进程能可靠完成 |
| 大图片、音频、视频、生成文件 | 本地文件目录；生产评估对象存储 | 不把大二进制塞进关系数据库 |
| 需要逐步展示模型内容 | SSE | 只需后台执行和看最终结果：用"提交 + 查询状态" |

已有项目默认延续其合理架构。只有触犯强制底线、满足不了需求、或继续维护的风险明显高于迁移风险时，才提出**局部**迁移；不为了让目录和规范长得一样而整体重构。

## 开发路径：后端先行还是纵向切片

默认**后端先行**：先把模型调用、数据处理、状态流转和 API 做成可独立验证的核心能力，再投入正式前端，避免在 Agent 效果还没成立时打磨界面。

当人工确认、可视化编辑、画布、音视频时间轴或多轮交互**本身就是 Agent 能力的一部分**时，改用**纵向切片**：一个最小用户任务 → 最小界面 + 最小后端 + 真实模型 → 端到端验证 → 再逐条扩展。

```text
路径 A｜后端先行（默认）：后端能力 → API / 自动化验证 → Agent 效果验证 → 正式前端 → 联调
路径 B｜纵向切片：一个最小任务的界面 + 后端 + 真实模型端到端跑通 → 再扩展下一条
```

两条路径共同的判断：
- 核心能力没验证通过，不进入大规模正式前端开发；
- 交互决定 Agent 是否可用时，尽早做最小真实界面，别把 UI 当成最后的"展示壳"；
- 前端一次只做一个主要终端，稳定后复用同一套后端扩展其他终端。

产出是长文档、复杂结构、多轮对话、图片视频或需要人工确认时，只看 Swagger 里的 JSON 判断不了质量，要有**最小验收界面**。判定只看一条：这个界面会不会保留到正式产品。不会 → 临时验收界面（单个 HTML 放 `backend/static/`，FastAPI 直接挂载，原生 JS + `fetch`，不引脚手架）；会 → 纵向切片，按正式前端标准做（见 agent-frontend-stack）。

## 工作顺序

```text
读需求、现有代码和环境
→ 需求有缺口：先分类再问（见下）
→ 输出《技术适配声明》，等用户确认
→ 写当前阶段技术开发文档
→ 只开发当前阶段
→ 跑双层验收
→ 用户按验收清单亲自操作 → 修复 → 再验收
→ 通过后进入下一阶段
```

这是"开发—运行—测试—修复—验收"的循环，不是一次性生成成品。

**用户直接要代码时**（"把方案定下来，再把核心代码写出来"这类一次性请求），不要停下来等确认：把《技术适配声明》的要点（采用的默认方案、触发的按需模块、偏离项、待用户决定的问题）写进方案文档或 README 的开头，然后接着写代码。待决定的问题用决策卡列出，并标明代码里先按哪个推荐项实现，改起来动哪个文件。确认这一步的目的是让取舍可见，不是卡住交付。

**需求缺口怎么问**：会改变目标用户、核心任务、成本、安全、隐私或交付范围的，**必须问**，一次不超过 5 个，每个用"问题 / 选项 / 推荐 / 不选的后果"四行写，对方可以只回"按推荐"；其余用本技能的默认值填上、写明理由，让用户确认一次。效果标准写不出数字时不要逼，记为"待样例打分"，第一次真实冒烟时用样例定（见 `references/validation.md`）。

**开工前的环境自检**，如实报告：现有项目的 README、目录、启动方式、依赖、测试、未提交修改和已有数据（先理解再改，不先重构）；解释器真实版本和路径；Git 是否可用；有没有模型 Key（**没有 Key 不阻塞开发，只阻塞最终验收**，开发期用占位值 + mock 推进）；端口和外部依赖是否冲突。

## 强制底线速查（A 层）

完整细则和理由见 `references/engineering-rules.md`。下面这些任何阶段都不得违反：

1. **密钥**只放后端可读、不进仓库的载体（本地 `.env` 加入 `.gitignore`，只提交 `.env.example`；线上用平台 Secret）。不进前端、不进构建产物，不在对话、日志、截图、提交记录里回显。
2. **重要业务数据、长任务状态、人工确认点必须持久化**，进程重启后能恢复，不能只放内存。
3. **每个 API 定义请求、响应、错误**；错误统一为 `{"error": {"code", "message"}}`，不泄露堆栈。SSE 必须以 `done` 或 `error` 事件收尾。
4. **模型输出必须结构校验**；模型调用处理超时、失败、有限重试，**包括 SDK 初始化阶段的失败**。
5. **高风险、不可逆、涉及费用或对外发送的动作**由确定性代码和人工确认约束，不交给模型自主决定。
6. **上传文件**校验格式、真实类型、大小、安全文件名；日志不记密钥、密码、完整用户文档。
7. **多人使用的业务记录从第一张表起带归属字段**（如 `owner_id`），暂不登录时写固定默认归属；权限在后端按当前使用者过滤，前端隐藏按钮不算权限控制。
8. **会产生费用的云资源**，创建前先告知费用量级并等用户确认。
9. **不删除已有功能、测试、用户数据**；会造成迁移成本或客户端不兼容的技术替换先确认。
10. **不用 mock 结果冒充真实模型验证**；不靠删测试、隐藏报错、降低标准来"通过"。没有真实 Key 时如实写"待验"。

## 默认目录结构

后端先行时的默认结构；纵向切片时可同时建最小 `frontend/`。用不到的目录不建空壳。已有项目延续已有结构。

```text
<项目>/
├── backend/
│   ├── app/
│   │   ├── api/          # 路由
│   │   ├── core/         # 配置、安全、日志
│   │   ├── models/       # 数据库模型（用数据库时）
│   │   ├── schemas/      # 输入输出结构
│   │   ├── services/     # 业务逻辑、AI、Agent、RAG；数据读写集中在 repository
│   │   │   └── prompts/  # Prompt 模板独立文件
│   │   └── main.py
│   ├── static/           # 临时验收界面（需要时）
│   ├── tests/            # pytest
│   ├── alembic/          # 用关系型数据库时
│   ├── .env.example
│   └── requirements.txt  # 或 pyproject.toml + 锁文件，二选一
├── frontend/             # 选了 Web 终端或纵向切片时
├── scripts/              # 冒烟脚本、重启恢复检查等
├── data/                 # 本地数据库、结构化文件、上传、向量数据（加入 .gitignore）
└── docs/                 # 需求、技术适配声明、阶段文档、验收记录
```

数据读写集中在 repository 层：本地用 SQLite，上线时可以换成托管数据库或平台数据网关，两种实现跑同一套接口测试。

## 双层验收（缺一不可）

涉及模型调用的核心链路，两层都要做。细则、冒烟记录格式、效果评分法、重启恢复检查见 `references/validation.md`。

1. **mock 自动化测试**（每次开发完成必跑）：pytest，模型一律 mock、离线可跑；覆盖业务逻辑、状态流转、参数校验、错误路径、模型输出解析器。至少 5 条有意义的用例，不拿空测试充数。
2. **真实模型端到端冒烟**（阶段验收前必做）：mock 永远覆盖不到认证与 SDK 初始化、真实网络的超时限流、真实输出质量、真实延迟。每种模型调用契约、每条关键用户链路，至少跑通一条"真实输入 → 真实模型 → 持久化 / 返回 → 用户可查看"的完整路径。**冒烟结果由脚本自动写入记录文件**，不在对话里口头说"跑过了"。

做不到真实冒烟（没 Key）时，阶段只能算"待验，未完成"，可以先交进度，但不宣布完成。

## 你可以自主做的事

在不违反底线、不破坏已验证契约的前提下：引入当前阶段必要的辅助库（说明用途、记录版本）；为完成验收补测试、类型、日志和错误处理；在现有结构上做小范围重构；在技术适配声明里采用默认方案、启用按需模块或说明合理偏离；发现文档冲突时指出具体冲突并给出一个推荐处理方案。
